# ADR 0001: GitOps with ArgoCD and an app-of-apps tree

- Status: Accepted
- Date: 2026-11-15

## Context

The platform must be reproducible from a laptop to a real cluster, with an auditable deployment history and no imperative `kubectl apply` path to production. The same repository contains the application, its Helm chart, platform add-ons, policies and infrastructure bootstrap.

Two broad models were considered:

1. CI pushes rendered manifests directly to the cluster with credentials.
2. A cluster-resident controller reconciles the desired state from Git.

## Decision

Use ArgoCD as the only deployment mechanism below the bootstrap boundary.

- Terraform installs ArgoCD and registers the `meridian` AppProject and `meridian-root` Application.
- The root Application points at `deploy/gitops/app-of-apps`.
- Sync waves order the platform: namespaces (-30), monitoring (-25), cert-manager (-20), ingress/Kyverno/Rollouts (-10), cert-manager configuration and policies (-5), workloads (0). Monitoring comes before the charts that emit ServiceMonitor resources so their CRDs exist at admission time.
- Local and staging environments are generated by an ApplicationSet and auto-sync with prune and self-heal. Production is an explicit Application with no automated sync.
- Multi-source Helm Applications use a pinned upstream chart repository plus a values file from this repository (`$values` ref).
- The image bump is a Git commit. The release workflow commits to staging; production is a pull request.

## Consequences

- The cluster converges to Git; drift is corrected by self-heal.
- Rollback is a Git operation (revert) or an ArgoCD/Argo Rollouts operation with a follow-up Git reconciliation.
- Production requires a human Sync click. This is intentional: merge is authorization, sync is execution, and the canary is the gate.
- The repository must be reachable by the repo-server. Private repositories need a credential secret.
- Terraform and ArgoCD have a clean boundary: Terraform owns the cluster and the ArgoCD installation, not the workloads it reconciles.
- App-of-apps is simpler to reason about than generating Application CRs from CI, but it is a single root point of failure. The root Application is automated, so a bad root commit has a large blast radius; branch protection and review are mandatory.

## Alternatives considered

- **CI push (GitHub Actions + kubectl/Helm)** — requires long-lived cluster credentials in CI, provides no reconciliation loop, and hides drift. Rejected.
- **Flux** — viable and strong for this shape. ArgoCD was selected for its UI, ApplicationSet, sync waves and first-class Argo Rollouts integration in this demo.
- **One Application per environment without app-of-apps** — more bootstrap manifests and no platform ordering. Rejected.
